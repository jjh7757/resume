01

지원 동기

저는 여러 기술을 하나로 연결해 동작하는 상태로 만드는 일에 재미를 느낍니다.

학부 졸업연구로 IoT 자동 방지턱 시스템을 만들었습니다. 로드셀과 레이더로 속도를 재고, 카메라 영상을 객체 인식 모델로 판별하고, 그 결과로 액추에이터를 제어한 뒤, 내부망 장비의 데이터를 외부 클라우드 서버로 올려 웹에서 관제하는 구조였습니다. 3인 팀의 팀장으로서 센서 연동과 웹 관제, 전체 통합을 맡았는데, 각 부분이 따로 돌 때보다 서로 맞물려 하나로 동작하기 시작하는 순간이 가장 기억에 남았습니다. 이 연구는 학술대회 발표를 거쳐 2026년 8월 사물인터넷융복합논문지에 제1저자로 게재됐습니다.

LLM 에이전트가 정확히 같은 성격의 일이라고 생각했습니다. 모델 하나로 끝나지 않고 검색과 도구 호출, 상태 관리, 실패 처리를 엮어야 비로소 동작하기 때문입니다. 그래서 AI 에이전트 트랙에 들어와 RAG와 에이전트 구조를 공부했고, 배운 것을 실제로 확인하기 위해 공공문서 질의응답 서비스를 만들어 직접 구축한 AWS 환경에 올려 운영하고 있습니다. 벡터 검색과 BM25를 결합한 하이브리드 검색을 쓰고, 인덱스 구축이 서버 기동을 막지 않도록 백그라운드로 분리했으며, 공개 URL이라 API 남용을 막는 요청 제한까지 붙였습니다.

만들어본 것과 띄워서 유지하는 것은 다른 일이라는 것을 이 과정에서 배웠습니다. 다만 제 프로젝트에는 실사용자가 거의 없어, 트래픽이 있을 때 무엇이 먼저 무너지는지는 아직 겪어보지 못했습니다. 실제 사용자를 두고 도는 시스템에서 그 부분을 이어서 배우고 싶어 지원했습니다.

02

직무 역량 / 본인의 강점

만든 것을 배포하고 유지하는 데까지 가져가는 것이 제 강점입니다.

모의투자 서비스를 만들 때 증권사 API에 초당 1건이라는 호출 제한이 있어, 전역 큐로 1.1초 간격을 강제해 해결했습니다. 그런데 배포 환경이 서버리스라는 점이 마음에 걸렸습니다. 확인해보니 인스턴스마다 메모리가 분리돼 큐가 따로 생기고, 동시 요청이 서로 다른 인스턴스로 가면 간격 보장이 깨지는 구조였습니다. 당장 장애가 난 것은 아니었지만 조건이 맞으면 반드시 재현될 결함이라 판단해, 상주 프로세스 한 개로 동작하도록 Docker 셀프호스팅으로 옮겼습니다. 기능을 추가하는 것보다 이미 동작하는 것의 전제를 의심하는 일이 더 중요할 때가 있다는 것을 여기서 배웠습니다.

이 경험이 이어져 지금은 배포 환경을 직접 만들어 쓰고 있습니다. git push 한 번으로 빌드부터 HTTPS 서비스까지 끝나고, 장기 액세스 키를 두지 않도록 매번 임시 자격증명을 받으며, SSH 포트를 열지 않고 접속합니다. 이전 프로젝트에서 저사양 서버 안에서 반복 빌드를 하다 디스크가 가득 찬 적이 있어, 빌드는 CI로 빼고 서버는 이미지를 받아 교체만 하도록 구성했습니다.

겪은 문제와 판단 근거를 글로 남기는 것도 습관입니다. 학습 내용을 매일 공개 저장소에 정리하고 있고, 배포 환경도 계획과 단계별 절차, 트러블슈팅을 문서로 남겼습니다. 최근 RAG 서비스를 올릴 때 그 문서대로 따라가니 막힌 지점이 하나뿐이었습니다. 기록이 실제로 시간을 줄인다는 것을 확인한 셈입니다.

아직 실사용자 트래픽을 감당해본 경험은 없습니다. 다만 만들고 띄우고 고치는 과정을 반복해왔기 때문에, 그 경험이 주어지면 빠르게 흡수할 수 있다고 생각합니다.

03

문제 해결 경험

배포 파이프라인을 만들면서 CI에서 클라우드 인증에 계속 실패한 적이 있습니다.

에러 메시지는 권한이 없다는 한 줄뿐이었습니다. 설정을 처음부터 다시 확인했지만 전부 맞았습니다. 인증 공급자도 등록돼 있었고, 역할 이름도 워크플로가 부르는 값과 글자까지 같았고, 신뢰 정책의 조건도 문서대로였습니다. 역할을 다시 만들어도, 시간을 두고 재시도해도 같았습니다.

원인 파악이 어려웠던 이유는 클라우드 쪽이 “역할이 없음”과 “신뢰 정책 불일치”를 같은 메시지로 응답하기 때문이었습니다. 역할 이름을 추측해 알아내는 것을 막으려는 설계인데, 덕분에 저는 계속 엉뚱한 곳을 의심했습니다.

세 번쯤 실패한 뒤 접근을 바꿨습니다. 설정을 더 들여다보는 대신, CI가 실제로 무엇을 보내는지 직접 출력해봤습니다. 워크플로에 임시 단계를 넣어 토큰의 내용을 찍어보니, 식별자 형식에 저장소와 소유자의 숫자 ID가 들어 있었습니다. 클라우드 콘솔이 만들어준 신뢰 정책은 ID가 없는 예전 형식이어서 서로 맞지 않았던 것입니다. 이름 변경에 영향을 받지 않도록 형식이 바뀌었는데 콘솔이 따라오지 못한 상태였습니다.

두 형식을 모두 허용하도록 정책을 고치니 바로 통과했습니다. 이 일에서 얻은 것은 특정 지식보다, 에러 메시지가 모호할 때는 추측을 반복하는 것보다 실제 값을 확인하는 편이 빠르다는 판단 기준이었습니다. 이후 같은 원인으로 막히지 않도록 이 내용을 문서로 남겨두었습니다.

04

협업 경험

학부 캡스톤 프로젝트에서 3인 팀의 팀장을 맡았습니다.

시스템이 센서, 객체 인식, 제어, 웹 관제로 나뉘어 있어 역할을 나눴습니다. 저는 센서 연동과 웹 관제, 그리고 전체 통합을 맡았고 팀원이 객체 인식 모델 학습을 담당했습니다. 통합을 맡으면서 알게 된 것은, 각자 만든 것을 붙이는 일이 기술 문제이기 전에 합의 문제라는 점이었습니다.

가장 손이 많이 간 부분이 경계였습니다. 한쪽 보드가 잰 속도를 다른 보드로 넘길 때 어떤 값을 어떤 형식으로 언제 보낼지, 객체 인식 결과를 제어 로직이 받을 때 클래스명과 신뢰도 기준을 어떻게 정할지 같은 것들입니다. 각자 자기 쪽에서는 문제가 없는데 붙이면 동작하지 않는 일이 반복돼서, 형식을 먼저 정하고 각자 구현하는 순서로 바꿨습니다.

의사결정에서도 기준을 맞추려 했습니다. 속도 측정을 로드셀만으로 할지 레이더를 추가할지 논의했을 때, 단일 센서는 측정값이 틀려도 검증할 방법이 없다는 이유로 두 방식을 함께 쓰기로 했습니다. 결과적으로 구간 속도와 순간 속도를 교차 검증하는 구조가 됐고, 이 부분은 논문에서도 설계의 핵심으로 서술했습니다.

혼자 하는 프로젝트가 더 많았지만, 통합을 맡아본 경험 덕분에 남이 만든 것과 맞물리게 만드는 일이 어떤 일인지는 알고 있다고 생각합니다.

05

실패했거나 어려웠던 경험

쇼핑몰의 다크패턴을 자동으로 찾아내는 도구를 만들다가 중간에 접은 적이 있습니다.

카운트다운 타이머가 재방문 시 초기화되는지, 결제 단계마다 총액이 조용히 바뀌는지를 자동으로 검사하는 프로토타입이었습니다. 정답을 아는 테스트 사이트를 여섯 개 만들어 검증했고 8건 모두 정확히 탐지, 오탐은 없었습니다. 여기까지는 잘 됐다고 생각했습니다.

실제 쇼핑몰 네 곳에 돌려보니 결과가 달랐습니다. 다크패턴은 한 건도 나오지 않았고, 대신 제 도구의 버그가 네 개 나왔습니다. 캐러셀을 카운트다운으로 잘못 읽는 오탐, 옵션 선택 직후 클릭이 경합하는 문제, 페이지 구조상 보이지 않는 영역을 놓치는 문제 같은 것들이었습니다. 버그는 고쳤지만 더 큰 문제가 남았습니다.

표본이 편중돼 있었습니다. 제가 고른 곳은 브랜드 이미지를 신경 쓰는 쇼핑몰이라 애초에 다크패턴이 있을 가능성이 낮았습니다. 그리고 더 근본적으로, 이 검사에 돈을 낼 사람이 있는지를 확인한 적이 없었습니다. 정작 검사가 필요한 곳은 검사받고 싶어 하지 않을 가능성이 높았습니다.

도구를 더 정교하게 만들 수도 있었지만, 만들 가치가 있는지를 확인하지 않은 채 시간을 더 쓰는 것이 맞는지 판단이 서지 않았습니다. 그래서 보류하기로 하고 왜 접는지를 문서로 정리했습니다.

기술적으로 완성하는 것과 만들 가치가 있는지 판단하는 것은 다른 일이며, 후자를 먼저 확인해야 한다는 것을 배웠습니다. 지금은 무엇을 만들기 전에 누가 왜 쓸지를 먼저 적어둡니다.

06

입사 후 포부

당장은 맡은 것을 끝까지 가져가는 사람이 되는 것이 목표입니다.

지금까지 만든 것들은 사용자가 거의 없는 개인 프로젝트였습니다. 그래서 실제 트래픽이 있을 때 무엇이 먼저 무너지는지, 장애가 났을 때 어떤 순서로 확인해야 하는지는 아직 겪어보지 못했습니다. 실사용자를 두고 도는 시스템을 맡게 되면, 기능을 붙이는 일뿐 아니라 왜 느린지, 왜 실패하는지를 데이터로 설명하는 일을 할 수 있게 되고 싶습니다.

그다음으로는 LLM 기능의 품질을 측정하는 쪽에 기여하고 싶습니다. RAG를 공부하면서 검색 평가와 답변 평가를 분리해서 재야 원인을 구분할 수 있다는 것을 배웠는데, 정작 제가 만든 서비스에는 아직 평가 체계를 붙이지 못했습니다. LLM 기능은 “잘 되는 것 같다”로는 개선할 수 없고 측정 기준이 있어야 한다고 생각하기 때문에, 실무에서 이 부분을 제대로 해보고 싶습니다.

길게는 모델이 바뀌어도 흔들리지 않는 구조를 만드는 사람이 되고 싶습니다. 모델과 프레임워크는 빠르게 바뀌지만, 무엇을 측정할지와 실패했을 때 어떻게 안전하게 떨어뜨릴지는 덜 바뀐다고 봅니다. 지금도 배운 것과 겪은 문제를 계속 기록하고 있는데, 이 습관을 팀 안에서도 이어가고 싶습니다.
